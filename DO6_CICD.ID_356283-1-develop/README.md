Проект представляет собой законченную реализацию производственного конвейера непрерывной интеграции и доставки (CI/CD) для C-приложений на базе платформы GitLab CI/CD. В репозитории развернут и настроен отказоустойчивый распределенный конвейер, автоматизирующий процессы сборки исполняемых бинарных файлов, глубокого статического анализа соответствия кодстайлу Google Style, комплексного интеграционного тестирования с верификацией потоков ввода-вывода, изолированного безопасного деплоя на удаленный производственный сервер по протоколам SSH/SCP с ручным подтверждением (manual gate), а также передачи оперативных телеметрических уведомлений о статусе выполнения каждого этапа в Telegram-канал через Telegram Bot API.

---

## О проекте

Современные стандарты разработки программного обеспечения требуют минимизации ручных операций и исключения человеческого фактора на всех этапах жизненного цикла продукта. Данный проект направлен на построение надежного автоматизированного релизного конвейера, обеспечивающего соблюдение следующих инженерных целей:

1. **Автоматизация релизного цикла и сокращение Time to Market (TTM)**  
   Исключение ручной сборки, ручного запуска линтеров и локального прогона тестов позволяет разработчикам передавать изменения в основную кодовую базу через коммиты в систему контроля версий, получая готовый к развертыванию релизный артефакт в течение нескольких секунд.
2. **Гарантия стабильности и предсказуемости кодовой базы (Fail-Fast)**  
   Пайплайн спроектирован по принципу строгого последовательного контроля качества: любые отклонения от стандартов кодирования, ошибки компиляции или непройденные интеграционные тесты немедленно прерывают конвейер, блокируя распространение дефектного кода на последующие стадии и продуктивную среду.
3. **Архитектура распределенного GitLab Runner**  
   Сборочный процесс отделен от центрального управляющего сервера GitLab. Все задачи выполняются на выделенном хосте GitLab Runner с shell-исполнителем, обладающим изолированным рабочим окружением, предустановленным инструментарием сборки (GCC, Make, Clang-Format, cURL) и настроенным SSH-туннелированием к целевому серверу.
4. **Управляемость и безопасность релизов (Manual Deployment Gate)**  
   Внедрение механизма ручного подтверждения финальной стадии поставки гарантирует, что перенос бинарного файла на production-сервер происходит только по явному решению инженера после успешного завершения всех предварительных проверок.

## Ключевые навыки и освоенные концепции

В процессе проектирования и внедрения инфраструктуры CI/CD были освоены и применены на практике следующие ключевые инженерные компетенции:

- **Проектирование декларативных многостадийных пайплайнов в `.gitlab-ci.yml`**  
  Декомпозиция релизного цикла на строго упорядоченные стадии (`stages: build, style_check, test, deploy`), изоляция рабочих директорий джобов, управление очередями и зависимостями этапов выполнения.
- **Управление артефактами сборки (`artifacts` и `expire_in`)**  
  Конфигурирование механизмов захвата скомпилированного бинарного файла `./src/DO` в качестве долговременного артефакта стадии сборки с автоматическим сроком хранения в 30 дней (`expire_in: 30 days`), обеспечивающего доступность бинарника для аудита, тестирования и скачивания через интерфейс GitLab.
- **Строгий статический анализ кода (Google Style & Clang-Format)**  
  Настройка линтера `clang-format` с использованием официальной конфигурации Google Style (`.clang-format`). Использование флагов `-n` (сухой прогон без модификации файлов) и `-Werror` (трактовка любых предупреждений и стилистических расхождений как критических ошибок с ненулевым кодом завершения) для абсолютной гарантии чистоты исходного кода.
- **Разработка автоматизированных интеграционных тестов на Bash**  
  Написание тест-сьюта (`test.sh`), осуществляющего глубокую проверку бинарного файла: позитивные тесты с валидацией возвращаемых текстовых строк для всех корректных входных аргументов, а также негативные тесты на обработку некорректных аргументов, пустых входных данных и избыточного количества параметров с проверкой кодов возврата `exit 0` и `exit 1`.
- **Безопасная доставка по протоколам SSH/SCP с ручным подтверждением (`when: manual`)**  
  Организация доставки артефактов без использования интерактивных паролей на основе ключевых пар SSH (ED25519/RSA). Реализация атомарного сценария деплоя: загрузка бинарника через `scp` во временную изолированную директорию `/tmp/` с последующим перемещением через `ssh` в системную директорию исполняемых файлов `/usr/local/bin/` с контролируемым повышением привилегий через `sudo`.
- **Интеграция телеметрии и мониторинга через Telegram Bot API**  
  Реализация механизма обратной связи в секции `after_script` каждого джоба. Выполнение HTTP POST-запросов утилитой `curl` к эндпоинту `sendMessage` с передачей имени задачи и динамической переменной окружения `$CI_JOB_STATUS` (`success` / `failed`), что обеспечивает мгновенное информирование команды инженеров о ходе выполнения конвейера.

## Архитектура и стек технологий

### Структура и этапы пайплайна

Конвейер состоит из 4 последовательных стадий, настроенных в декларативном манифесте `.gitlab-ci.yml`:

1. **Стадия `build` (`build_job`)**  
   - Подготовка исходных файлов и сборочных инструкций из каталога `code-samples`.
   - Запуск очистки и компиляции проекта через `make clean && make`.
   - Сохранение скомпилированного бинарного файла `DO` в хранилище артефактов на 30 календарных дней.
   - Отправка уведомления о статусе сборки в Telegram через `after_script`.
2. **Стадия `style_check` (`style_check_job`)**  
   - Копирование исходных текстов и файла конфигурации правил форматирования `.clang-format`.
   - Выполнение проверки линтером: `clang-format -n -Werror ./src/main.c`.
   - Аварийная остановка конвейера в случае обнаружения пробелов, лишних переносов или несоответствий Google Style.
   - Отправка уведомления о статусе проверки стиля в Telegram через `after_script`.
3. **Стадия `test` (`test_job`)**  
   - Запуск интеграционного скрипта тестирования `test.sh`.
   - Прогон полного набора тест-кейсов над бинарным файлом `DO`.
   - Отправка уведомления о статусе тестирования в Telegram через `after_script`.
4. **Стадия `deploy` (`deploy_job`)**  
   - Блокировка автоматического запуска с помощью директивы `when: manual`.
   - Выполнение скрипта деплоя `deploy.sh` только после явного подтверждения инженером.
   - Беспарольная передача файла по SCP на целевой хост `192.168.1.103` и установка в `/usr/local/bin/DO`.
   - Отправка финального уведомления о статусе доставки в Telegram через `after_script`.

### Схема взаимодействия компонентов инфраструктуры

```text
+-------------------+
|   GitLab Server   |
|   (Code & CI/CD)  |
+-------------------+
          |
          | Git Clone / Trigger Job
          v
+-------------------------------------------------------------------+
|                        GitLab Runner Node                         |
|                                                                   |
|  +---------------+     +--------------------+     +-------------+ |
|  |   build_job   | --> |  style_check_job   | --> |  test_job   | |
|  | (Make -> DO)  |     | (clang-format -n)  |     |  (test.sh)  | |
|  +---------------+     +--------------------+     +-------------+ |
|                                                          |        |
|                                                          v        |
|                                                   +-------------+ |
|                                                   | deploy_job  | |
|                                                   |  (manual)   | |
|                                                   +-------------+ |
+-------------------------------------------------------------------+
          |                                                 |
          | SCP / SSH (Key Auth)                            | HTTPS POST
          v                                                 v
+-----------------------------------+             +-------------------+
|      Target Production Server     |             |  Telegram Bot API |
|      IP: 192.168.1.103            |             |  (Telegram Chat)  |

```

## Инструкция по сборке, тестированию и запуску

### 1. Подготовка и регистрация GitLab Runner

Для выполнения сборочных задач необходим выделенный агент GitLab Runner, развернутый на локальной или виртуальной машине.

Установка пакета gitlab-runner (для Debian/Ubuntu):
```bash
curl -L "https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh" | sudo bash
sudo apt-get install -y gitlab-runner
```

Регистрация раннера в репозитории:
```bash
sudo gitlab-runner register \
  --non-interactive \
  --url "https://gitlab.com/" \
  --registration-token "<REGISTRATION_TOKEN>" \
  --executor "shell" \
  --description "production-shell-runner" \
  --tag-list "cicd,build,deploy" \
  --run-untagged="true" \
  --locked="false"
```

Запуск и проверка статуса службы:
```bash
sudo systemctl enable --now gitlab-runner
sudo systemctl status gitlab-runner
```

### 2. Локальное воспроизведение шагов сборки и проверки стиля

Перед коммитом в репозиторий рекомендуется воспроизвести шаги пайплайна локально.

Сборка исполняемого файла:
```bash
cd ./src
make clean
make
```

Проверка соответствия стилю Google Style:
```bash
clang-format -n -Werror ./src/main.c
```
Если команда не выводит сообщений и возвращает код 0, проверка стиля пройдена успешно.

### 3. Локальный запуск интеграционных тестов

Прогон интеграционного набора тестов осуществляется выполнением скрипта:
```bash
cd ./src
chmod +x ./test.sh
bash ./test.sh
```

В процессе выполнения тестируются следующие сценарии:
- Запуск с аргументом `"1"` -> ожидается вывод `"Learning to Linux"`
- Запуск с аргументом `"2"` -> ожидается вывод `"Learning to work with Network"`
- Запуск с аргументом `"3"` -> ожидается вывод `"Learning to Monitoring"`
- Запуск с аргументом `"4"` -> ожидается вывод `"Learning to extra Monitoring"`
- Запуск с аргументом `"5"` -> ожидается вывод `"Learning to Docker"`
- Запуск с аргументом `"6"` -> ожидается вывод `"Learning to CI/CD"`
- Запуск с аргументами `"7"` и `"0"` -> ожидается вывод `"Bad number!"`
- Запуск без аргументов (`./DO`) -> ожидается вывод `"Bad number of arguments!"`
- Запуск с избыточным числом аргументов (`./DO 1 2 3`) -> ожидается вывод `"Bad number of arguments!"`

При успешном прохождении всех тестов скрипт завершает работу с кодом `0`.

### 4. Настройка беспарольного доступа по SSH и симуляция деплоя

Для выполнения задачи `deploy_job` пользователь, под которым запущен GitLab Runner (`gitlab-runner`), должен иметь возможность подключаться к целевому серверу без ввода пароля.

Генерация ключевой пары на хосте раннера:
```bash
sudo -u gitlab-runner ssh-keygen -t ed25519 -C "gitlab-runner@ci" -N "" -f /home/gitlab-runner/.ssh/id_ed25519
```

Копирование публичного ключа на целевой сервер (`192.168.1.103`):
```bash
sudo -u gitlab-runner ssh-copy-id -i /home/gitlab-runner/.ssh/id_ed25519.pub lenyldes@192.168.1.103
```

Настройка беспарольного выполнения команды перемещения на целевом сервере:
В файл `/etc/sudoers` (или `/etc/sudoers.d/ci-deploy`) на целевом сервере `192.168.1.103` добавляется директива:
```text
lenyldes ALL=(ALL) NOPASSWD: /bin/mv /tmp/DO /usr/local/bin/DO, /usr/bin/mv /tmp/DO /usr/local/bin/DO
```

Проверка скрипта развертывания:
```bash
cd ./src
chmod +x ./deploy.sh
bash ./deploy.sh
```

Верификация развернутого файла на целевом хосте:
```bash
ssh lenyldes@192.168.1.103 "/usr/local/bin/DO 6"
# Ожидаемый вывод: Learning to CI/CD
```

### 5. Настройка Telegram-оповещений

Для отправки уведомлений в Telegram используется официальный REST API.

Создание бота и получение учетных данных:
1. В Telegram открыть диалог с `@BotFather` и выполнить команду `/newbot`.
2. Сохранить выданный токен API (например, `8622863012:AAHZXHy8AWsuvrEcY0GYlvUKiAsQZ0PT7bA`).
3. Получить идентификатор целевого чата или пользователя (`chat_id`), написав боту `@userinfobot` или вызвав эндпоинт `https://api.telegram.org/bot<TOKEN>/getUpdates`.

Проверка отправки тестового уведомления через cURL:
```bash
curl -s -X POST https://api.telegram.org/bot8622863012:AAHZXHy8AWsuvrEcY0GYlvUKiAsQZ0PT7bA/sendMessage \
  -d chat_id=282195596 \
  -d text="CI/CD test message: pipeline is running"
```

Рекомендация по безопасности для Production:
В производственной среде токен бота и идентификатор чата не должны храниться в открытом виде в репозитории. Их следует выносить в защищенные переменные GitLab CI/CD (**Settings** -> **CI/CD** -> **Variables**):
- `TELEGRAM_BOT_TOKEN` (Masked, Protected)
- `TELEGRAM_CHAT_ID` (Protected)

И вызывать в `.gitlab-ci.yml` через переменные окружения:
```yaml
after_script:
  - curl -s -X POST https://api.telegram.org/bot${TELEGRAM_BOT_TOKEN}/sendMessage -d chat_id=${TELEGRAM_CHAT_ID} -d text="${CI_JOB_NAME} - ${CI_JOB_STATUS}"
```
